# MCP execution modules

`server.py` exposes model tools, `tasks.py` bridges scientific environments, `jobs.py` stores durable requests, and `runner.py` executes one job. `pipeline.py` separates CPU preparation from GPU groups. `backends.py` manages local/Slurm execution, `kubernetes.py` finite Kubernetes Jobs, `fleet.py` endpoint selection and verified collection, and `endpoint.py` the file-transfer agent, and `metrics.py` sampled GPU activity.

Configuration and operational requirements are in [MCP execution](../../../docs/mcp-execution.md) and [prediction servers](../../../docs/prediction-servers.md). No site-specific endpoint configuration belongs in these modules. Test scheduling, transport failures, scientific cache reuse and terminal receipts before running large workloads.

`make_backend` loads only the selected adapter. One GPU host uses `local`, even when MCP is accessed over SSH; one Slurm cluster uses `slurm`. A pool is optional for combining workers. The feature preparation, prediction and scoring stages also operate with a single backend.

`placement.py` assigns whole requests with persistent formula/precursor affinity. `workers.py` validates model identities, runs each worker's complete scientific pipeline and transfers final artifacts only. The coordinator needs no scientific runtime. Preparation, native HDF5, cache publication, scoring and viewer structure rendering stay on the selected SSH machine, or on the selected cluster's shared storage. `worker_scheduler.py` relays finite Kubernetes CPU/GPU Jobs while keeping API credentials on the coordinator. `scoring.py` runs supplied-candidate scoring in the worker's scientific interpreter. Existing coordinator-prepared jobs drain through the compatibility controller.

`features.py` owns each worker's detached feature backend: bounded CPU workers publish prepared entries and ready files, a durable queue deduplicates compatible predictions across unknowns, and `cpu_pool.py` reserves preparation/assembly processes independently from cache-only scoring services. Prepared groups enter the shared GPU queue and release their GPU allocation after native HDF5 output closes. Separate bounded CPU output services use `raw_outputs.py` to decode worker-local HDF5 directly into the shared cache. Their allocations are reused across groups. `preparation.py` defines the preparation/scoring file boundary. The frontend accepts requests and reads status; it does not schedule work. A driver reconciles backend state once per tick, and Slurm accounting is batched across active jobs.

`conditions.py` retains immutable shared runtime snapshots beyond per-feature cleanup and recovers legacy references from recorded consumers/native groups. Worker-owned scoring/publication records are excluded from standalone local, Slurm and Kubernetes scheduling, including inventory probes. CPU services can retire between tasks at configured lifetimes and return unfinished assignments without repeating completed inference.

`scheduling.py` owns detached local dispatch; `admission.py` manages production canaries, environment holds and independent prediction, CPU output/scoring and delivery budgets. Workers publish state without driving the scheduler. Compact live-job and parent/child indexes keep closed history out of scheduling scans. The recurring resource scan skips virtual feature and worker-owned task files after discovering legacy allocations owned by that scheduler.

`network.py` gives execution writes (submission, cleanup, cancellation), polling/control reads and artifact transfers independent bounded queues and executors. Colocated nonterminal status reads use the worker's configured filesystem; one RPC health owner per endpoint and terminal worker verification remain. The pool stages a bounded look-ahead at local endpoints while their own backends enforce GPU execution limits. Remote completion manifests make interrupted collection resumable. CPU parents share complete, expiring PubChem response snapshots to avoid repeating identical queries.

`cpu.py` plans independent feature concurrency from explicit core/RAM budgets and reports preparation, scoring, prediction waits and scheduler queues separately. `plan_cpu_concurrency` and CLI `plan-cpu` are read-only; apply measured host settings through setup and a controlled coordinator reload.

Preparation and scoring have explicit `feature_preparation_workers` / `feature_scoring_workers` limits; their sum replaces the legacy `feature_cpu_workers` total when set. Setup starts at 2 preparation services, 0.5 scoring services and 1 output/cache service per configured GPU slot, rounding up each stage. `max_cpu_jobs: auto` derives the CPU-service admission budget from those stages; explicit host caps remain supported. Native GPU featurization and writer processes use their separate model settings.
