# CPU preparation, GPU prediction and CPU scoring

Use one execution backend per MCP server. For a single GPU machine, run MCP on that machine with `mcp.backend: local`, including when the client connects over SSH. Its GPUs consume one shared local queue; no server pool is required. For one Slurm cluster, use `slurm`; for one Kubernetes cluster, use `kubernetes`. Select `pool` explicitly only when distributing work across multiple independently configured workers. The backend factory loads only the selected adapter. Start with one verified backend before adding a pool.

The default feature pipeline has four stages: CPU candidate preparation, shared GPU prediction batches, CPU output publication/scoring, and result collection. Preparation and scoring have independent process budgets. GPU jobs consume prepared work while CPU services prepare later features and publish earlier predictions. A completed prediction queue can be idle while scoring finishes; inspect stage backlogs before treating that as GPU starvation.

For a server pool, `mcp.feature_placement: workers` places complete requests on a scientific worker. The coordinator accepts requests, selects workers, monitors execution and collects final results. CPU preparation, grouped GPU prediction, CPU decoding/scoring and viewer structure rendering run on the selected SSH machine. Slurm and Kubernetes stages use their cluster's shared storage and separate CPU/GPU allocations; they need not occupy the same physical compute node. A dispatch-only coordinator needs no model interpreter, weights or PubChem index. Setup records the approved model identities for request validation.

Each worker uses backend-owned preparation lists and shared prediction groups, described under Resource settings. It inspects spectra, retrieves and validates candidates, and checks its raw-prediction cache before requesting GPUs. A complete cache hit needs no GPU job or native entry preparation. Formula and precursor-mass affinity keep likely overlapping pools on the same worker; exact scientific cache keys determine reuse. Direct forward-prediction/scoring requests also run on their selected worker. The optional `feature_placement: coordinator` compatibility mode prepares and scores on the coordinator and sends only GPU groups to endpoints.

CPU parents also share complete PubChem responses under the job root's `pubchem-responses` directory. Identical queries have one network owner; response snapshots retain the query, request body and fetch time. `mcp.pubchem_cache_ttl_seconds` defaults to 86400 and zero disables reuse. Errors and asynchronous waiting responses are not cached. This reduces repeated retrieval work across unknowns while preserving each feature's filtering, scoring and provenance. The shared PubChem request budget still applies to cache misses.

For missing spectra, the orchestrator submits an internal `model_inference` job. GLACIER's native entry preparation runs in the CPU stage and writes prepared entries into the job directory. Its GPU stage uses native `run_shard`, including its CPU featurization workers, batch prefetching and parallel HDF5 writers. ICEBERG prepares molecular identities and condition rows on CPU, then invokes its native `predict_smis` with parallel GPU workers. Native featurization still runs in the predictors; ICEBERG's generated fragment graphs require its generator. Both models retain their selected weights, adduct, instrument, energies, fragments and scientific cache identities.

Native HDF5 writes use GPU-node scratch and publish into that worker's shared job directory. The GPU allocation ends before separate CPU output services decode and cache predictions. The preparation/scoring CPU pool scores each unknown and renders its viewer structures. Only final results, reports, structure renderings and execution receipts return to the coordinator; native HDF5 and prediction caches stay on the worker. Successful native intermediates can be removed after validated cache publication. Final feature directories are removed only after verified collection, while shared caches remain available.

New batch builders enter the reserved CPU pool immediately after planning. While reconciling a large feature list, the driver advances already planned groups after each 32 feature checks. A completed CPU builder can therefore enter the GPU queue before the entire reconciliation pass finishes. These progress checks preserve the group-construction budget and do not plan extra batches.

## Resource settings

Budget preparation/prediction, CPU output/scoring and final delivery independently. Once predictions are ready, a feature waiting for HDF5 decoding or cache-only scoring no longer occupies a preparation/prediction slot. In particular, `waiting_cpu` with a `scoring_job` is a scoring waiter; `waiting_cpu` without one still requires preparation. A verified result awaiting transfer, publication or cleanup belongs to final delivery. A feeder should bound each backlog and stop new admission when either downstream bound is reached. `request_window` in `mcp.admission` provides this accounting, including scheduler-confirmation waits; its CPU output/scoring limit defaults to the delivery limit. Persist accepted request and result rows atomically before clearing their claim markers, coalescing history updates rather than rewriting the full campaign history for each result.

`server_info.cpu_workload` reports `feature_execution_pending`, `feature_postprediction_pending` and `feature_delivery_pending` for requests visible on that coordinator. A companion importer's publication backlog belongs in that importer's own status. Scoring waiters and finished records awaiting import do not measure GPU demand.

An incremental importer must retain and replay its original claim receipt through registration and history persistence. A claimed source record with no registered job requires reconciliation against that receipt and the deterministic request ID before admission; do not reset its claim or repeat completed records. An orphaned claim can also block related ready features when source affinity permits only one active claim per formula.

With `mcp.feature_pipeline: true` (the default), the backend accepts feature requests independently from execution. `elucidate_spectra` submits a whole batch; individual `retrieve_atlas`, `search_pubchem_formulas` and `search_pubchem_mass` requests enter the same queue. A detached backend driver splits pending unknowns into balanced lists for the reserved preparation processes. Each worker performs formula inference, candidate generation and native entry preparation for several unknowns, publishes each feature's `ready.json` atomically, and proceeds immediately. Preparation holds no GPU allocation and never waits for predictions. Preparation services accept subsequent balanced lists and assemble native prediction batches. Separate scoring services consume ready per-feature scores, preserving preparation capacity while earlier predictions finish. They retire after `feature_worker_idle_seconds` without CPU work; choose this finite idle budget with the preparation host's queue latency and resource policy in mind.

The driver discovers ready files, combines compatible SMILES/adduct/instrument/energy requests across unknowns, and records shared prediction ownership in `feature-queue/queue.sqlite3`. Prediction groups use the configured duration/size policy and enter GPU queues directly, without another CPU scheduler allocation. Native inference keeps its parallel HDF5 writers and closes all output files before releasing the GPU allocation. The backend collects those files and queues a separate CPU publication task. Bounded, reusable CPU output services decode the native HDF5 directly into the validated shared prediction cache, without an intermediate JSONL export. GPU dispatch continues during collection and CPU publication. Conditions, exact weights, native implementation and cache identity must match. A feature already covered by queued or completed groups reuses them. Each SSH GPU host has one shared endpoint queue consumed by its available GPUs; Slurm endpoints submit finite jobs to Slurm. Cache publication precedes per-feature cache-only scoring tasks served by the preparation/scoring CPU pool. Scores, candidate provenance, output reports and evidence review remain specific to each unknown. A scoring cache miss fails instead of silently running a model on CPU.

Preparation lists have equal feature counts, which need not imply equal CPU time. Set independent preparation/assembly and scoring budgets with `feature_preparation_workers` and `feature_scoring_workers`. When scoring is unset, the legacy `feature_cpu_workers` total supplies the remainder. Scoring cannot borrow reserved preparation slots. CPU services receive ready assignments before the controller scans shared caches and plans large prediction groups. Services can reuse compatible scientific/runtime profiles across queue-policy changes; each task reads its own saved configuration. In the legacy total-based configuration, `auto` reserves half the pool, rounded up; a single-process pool shares preparation and scoring, and explicit preparation `0` enables shared operation. Explicit positive preparation/scoring counts take precedence over the legacy total. Bound and tune process counts from CPU/RAM measurements; the backend keeps accepting requests while lists run. CPU list workers, prediction groups and scoring jobs have separate durable receipts. Cancelling one unknown preserves shared work needed by others. `feature-service.json` records the detached driver; `scheduler-stop.json` stops admission without deleting requests or caches. The existing per-request pipeline remains available with `feature_pipeline: false` for single-task embedding and compatibility.

Shared conditions keep immutable runtime snapshots under `feature-queue/condition-configs`, independently of collected feature folders. Cleanup can remove an acknowledged feature while later unknowns reuse its condition. Older references are recovered from retained consumers or native jobs for that same condition; unavailable configuration leaves affected features in `waiting_configuration` without stopping unrelated work. Internal scoring and publication records belong to CPU services and cannot be submitted independently by resource schedulers. Whole-worker inventory uses the worker probe and does not run a raw endpoint scheduler.

The driver reconciles backend state once per tick and reads those results for all dependent features. Slurm accounting queries cover active jobs in a batch; missing accounting records fall back to the live queue. `mcp.task_slurm` can override resources by internal task name, including `prepare_feature_list` and `score_prepared_feature`, when preparation needs a different CPU partition or operating system. Configure and verify the actual compute-node environment during setup.

Once a feature has a scoring job, reconciliation checks that job directly. Its immutable prediction dependencies do not need another candidate-consumer traversal on every pass. Colocated status polling also avoids rewriting unchanged coordinator records. Endpoint timeouts retain assignments and surface transport errors without terminating the dispatcher.

Set machine-specific values in ignored `configs/local.yaml`. For a pool, CPU/GPU stage settings belong in each endpoint's host configuration, `feature_config` or `mcp` overrides. The coordinator's corresponding values govern only compatibility work that runs there.

| Setting under `mcp` | Meaning |
| --- | --- |
| `feature_placement` | Pool placement: `workers` runs complete requests on workers; `coordinator` retains central preparation/scoring with GPU endpoints. |
| `approved_model_identities` | Setup-verified weight and native-source hashes used by a thin coordinator; workers verify the full package and scientific identity before execution. |
| `max_concurrent_jobs` | Local GPU-job limit; `auto` uses one slot per detected, allowed GPU, or one CPU inference slot without GPUs. |
| `gpu_devices` | Optional list of physical GPU indices allowed for local jobs; `null` allows all detected GPUs. |
| `max_cpu_jobs` | Optional CPU-service admission cap. Default `auto` sums preparation + scoring + output limits for the feature pipeline; the compatibility path uses 2. Sleeping orchestrators do not occupy active CPU slots. |
| `feature_cpu_workers` | Legacy preparation/assembly + scoring total; default 3 for a single-GPU starting profile. Ignored when explicit preparation/scoring counts are set. |
| `feature_preparation_workers` | Dedicated preparation/assembly services. Setup starts at 2 per GPU slot. With legacy totals, `auto` reserves half rounded up, and `0` shares the pool. |
| `feature_scoring_workers` | Independent scoring services; setup starts at ceil(GPU slots / 2). `null` derives scoring from the legacy total. An explicit count requires a positive preparation count; their sum replaces the legacy total. |
| `feature_worker_idle_seconds` | Finite CPU worker reuse window for new preparation lists and scoring; default 60 seconds. |
| `feature_worker_max_seconds` / `feature_output_max_seconds` | Optional CPU service lifetimes. Finish the current task, then return unstarted assignments to another service. Set below the scheduler allocation time, allowing headroom for the longest individual task and startup. |
| `feature_prediction_groups` | Bound shared prediction groups awaiting completion; `auto` allows two per endpoint slot. |
| `feature_group_builds_per_tick` | Limit group construction before reconciling GPU queues and collecting completed work again; default 2. |
| `feature_queue_cache_mb` | SQLite page-cache budget per feature-driver connection, default 64 MiB. Tune from reconciliation timings and RAM headroom for large queues; pages are allocated as used. |
| `feature_cpu_output` | Default `true`: release GPU allocations before CPU-only HDF5 decoding and cache publication. `false` retains inline export for controlled comparisons. |
| `feature_output_workers` | CPU output-service limit; `auto` is the smaller of the effective preparation/scoring total and configured prediction capacity. Tune from decoding time, CPU/RAM budgets and GPU consumption. |
| `feature_output_idle_seconds` | Finite CPU output-service reuse window; default 60 seconds. Include scheduler latency when configuring remote allocations. |
| `cpu_preparation_workers` | GLACIER entry-preparation workers; `auto` caps the tuned count at the CPU allocation/affinity. GPU-stage featurization retains its model profile. |
| `scheduler_process` | Default `true`: one detached local dispatcher; workers publish state and wait. |
| `max_live_pipelines` | Cap live CPU pipelines including GPU/cache/CPU waiters; `auto` is CPU slots plus the prepared limit. |
| `route_canary` | Default `true`: one successful PubChem production request precedes bulk admission for that model/configuration. |
| `environment_failure_limit` | Default 3: hold new admissions for repeated classified environment errors; a failed environment canary holds immediately. |
| `worker_environment` | Explicit environment such as a verified `SSL_CERT_FILE`; cannot override scheduler GPU visibility or pipeline ownership. |
| `min_free_memory_gb` | Available-RAM floor for starting new local CPU jobs; default 2 GiB. Applied when the platform reports available RAM. |
| `max_prepared_jobs` | Pause new CPU preparations when this many orchestrators await inference. `auto` allows two per GPU, with a minimum of two. Already admitted CPU jobs may finish preparing. |
| `prediction_group_size` | `auto` estimates candidates from saved model throughput, target duration and energies, falling back to 4096. An integer sets an explicit size. CUDA batch size is independent. |
| `target_prediction_seconds` | Approximate GPU work per group, default 600 seconds; does not delay small requests. |
| `max_group_candidates` | Upper bound on automatically sized groups, default 32768. |
| `prepared_groups` | `auto`: two in-flight groups per endpoint slot, capped at eight per orchestrator. |
| `pool_rpc_workers` / `pool_transfer_workers` | Independent bounded endpoint control and artifact-transfer workers; defaults 4 and 2. |
| `pool_rpc_workers_per_server` | Control workers per physical `resource_group`; default 2. A value of 0 shares `pool_rpc_workers` across servers. |
| `pool_submission_workers` / `pool_submission_workers_per_server` | Execution-write workers for submissions, cleanup, cancellation and scheduler updates, independent of polling capacity; defaults 2 in shared mode and 1 per physical server. Each purpose has its own bounded waiting queue. |

For each worker with G allowed concurrent GPU slots, start with 2G preparation services, ceil(G/2) scoring services and G output/cache services. Round each stage up independently. For eight slots, set `feature_preparation_workers: 16`, `feature_scoring_workers: 4` and `feature_output_workers: 8`. The default `max_cpu_jobs: auto` derives 28 CPU-service admission slots, so no separate total is needed. Keep an explicit cap only when host limits require one; it may reduce simultaneous service activity. Use configured/authorized GPU capacity rather than instantaneous idle counts or a login node inventory. Setup saves separate stage counts in private host configuration. Preserve explicit host tuning and validate the ratio against CPU/RAM and scheduler budgets. These are process counts, not claims about CPU utilization. On an SSH or local host, process oversubscription can help when tasks wait on files or networks; include native GPU data-loader processes, memory, CPU pressure and storage throughput when tuning. Slurm/Kubernetes allocations must still fit their requested resources. When changing a running shared pool to reserved roles, let each old service finish its current task and exit before its unstarted assignments are returned; running predictions continue.

The RAM floor is an admission check, not a hard memory limit. Tune CPU slots, preparation workers, group size and model batch size together for the host. A larger prediction group amortizes Python startup, checkpoint loading and writer startup while retaining resumable groups. Native model processes still load their weights for each uncached group; the adapter does not keep a resident model across requests.

Scheduling probes the raw cache without waiting for a SQLite writer. A busy cache leaves that condition in `waiting_cache` while other conditions continue; it is never treated as a cache miss or a reason to duplicate inference. Cache corruption and configuration errors remain visible failures. CPU services perform decoding and validated cache writes independently from dispatch.

Cache readers use short transaction windows, including the final check for predictions published by another producer. This avoids a filesystem lock operation per spectrum on network storage while releasing read snapshots between windows. Prediction runs outside those read transactions; publication still validates every requested record before taking the writer gate.

The collection workers also verify transferred results, relocate result paths and finalize reports. A large report therefore does not block the placement loop. Results become complete only after that work finishes; remote cleanup still requires a saved checksum acknowledgement. Repeated storage-capacity errors hold new route admissions until the storage is repaired and the hold is explicitly resumed.

Pending cleanup keeps the backend live even after all prediction and scoring jobs finish. Durable `remote_cleanup_pending` flags recreate missing cleanup markers when status is read or written, using the worker queue for whole requests and the native-output queue for model groups. The dispatcher drains those acknowledgements before retiring. Idle GPUs with no remaining prediction work are expected; final delivery and cleanup still need verification.

### Size CPU stage jobs

`max_cpu_jobs: auto` derives the feature pipeline's CPU-service admission budget from preparation + scoring + output. Set an explicit integer only for a tighter host budget; this does not cap the model's internal DataLoader or writer processes. With the feature pipeline enabled, explicit `feature_preparation_workers` and `feature_scoring_workers` independently bound those services. The legacy total remains available when scoring is unset. Waiting feature requests are filesystem records and do not reserve CPU allocations. The compatibility path uses one resident parent per feature. GLACIER's `num_cpu_workers` controls featurization inside each native prediction process. Measure and tune these separately.

Use `server_info.cpu_workload` for jobs on the server and `server_info.backend.worker_execution` for pool workers' CPU/RAM observations, active features and phases. Distinguish active CPU work from prediction/cache waits and scheduler submissions. The worker's configured CPU pools and group look-ahead determine whether its GPUs have upcoming work. Submitted Slurm jobs have not necessarily started. Check host CPU samples and phases together; coordinator virtual feature records consume no scientific CPU slots.

Budget CPU cores and RAM for all resident parents after reserving capacity for the operating system, other users and local GPU inference workers. Measure each CPU job's complete process tree or cgroup, including scientific subprocesses, and add memory headroom. Check native thread pools against the per-job CPU allocation. On Slurm, use the intended compute-node/account capacity and scheduler policy; the login host's CPU count is not that budget. On Kubernetes, use the applicable requests, limits and remaining quota.

Call MCP `plan_cpu_concurrency` with `cpu_budget`, `memory_budget_gb`, `cpus_per_job`, `memory_per_job_gb` and an optional `max_jobs`. Without MCP:

```bash
msms-structure-elucidation plan-cpu \
  --cpu-budget 24 --memory-budget-gb 64 \
  --cpus-per-job 2 --memory-per-job-gb 4
```

The read-only planner returns a capacity ceiling and an `mcp_settings` fragment; insufficient budgets return no fragment. The example allows at most 12 parents. The fragment bounds both `max_cpu_jobs` and `max_live_pipelines`, including resident waiters. With Slurm, `max_live_pipelines` is the submission cap for CPU parents; `max_cpu_jobs` alone contributes to the automatic cap and does not impose a separate active-job limit. CPU parents keep their CPU/RAM allocations during prediction waits, so increasing their count can increase reservations without increasing useful CPU work.

Compare representative completed-feature throughput, preparation/scoring times, peak memory and prediction-wait fractions at increasing concurrency, keeping inputs, weights, energies and cache conditions fixed. Increasing concurrency only helps while the relevant resources and downstream capacity have headroom. Save measured limits and CPU task resources in ignored `configs/local.yaml`; a capacity ceiling is not a measured optimum. Configure `mcp.slurm.cpu` or Kubernetes CPU resources to match the measured job footprint. Apply changes through a controlled coordinator/dispatcher reload while retaining existing native jobs, request identities and partial results.

Tune the models differently. For ICEBERG, start with two parallel GPU workers per GPU and compare two to four, adjusting the batch size to fit their combined memory use. `models.simulator.num_gpu_workers` is the total across configured `cuda_devices`; the scheduler scales it to the GPUs allocated to each job. For GLACIER, keep one prediction process per GPU and increase `models.simulator.glacier.batch_size` until throughput plateaus or memory limits are reached. Keep CPU workers and writers fixed initially, then adjust them if native timing shows feature or writer waits. Save measured settings in `configs/local.yaml`.

Local scheduling uses one detached process per job root. Startup is arbitrated on local temporary storage; the driver holds one shared ownership lease. Waiting workers never schedule the queue. CPU-ready requests resume in FIFO order before new preparations, and compact live-job and parent/child indexes keep closed history out of scheduling scans. After an initial discovery pass, the resource scheduler filters virtual feature and worker-owned task markers before opening their files, retaining any legacy allocations it already owns. Its `active_jobs` and `ready_cpu` describe resource jobs and CPU services; feature accounting stays with the feature backend. A complete raw-cache hit uses a read snapshot without writer leases. Cancellation and failed-child propagation preserve the affected requests and evidence.

Large cache hits release their SQLite read transaction between bounded molecule groups so validated writers can commit. Cache publication takes a short shared writer lease after model generation and validation, preserving concurrent prediction. During a compatible versioned rollout, an operator can retain a verified legacy raw-adapter namespace with `MSMS_PREDICTION_CACHE_ADAPTER`; only recognized equivalent raw-generation implementations accept this setting. Different raw generation, weights or conditions still invalidate reuse. Preserve the namespace throughout a rolling upgrade so old and new workers share the same candidate ownership locks.

The local driver survives client disconnection and exits after 60 idle seconds. `scheduler-service.json` reports its host, PID, heartbeat and admission state. Write `scheduler-stop.json` in that root to stop scheduling without cancelling existing allocations; remove it only for an authorized resume. Restart the driver to apply configuration changes. Stop old dispatchers before upgrading and preserve requests, caches, checkpoints and partial results; never replace code underneath live workers. `scheduler_process: false` is for a caller that continuously owns and pumps the backend itself.

With Slurm, preparation/scoring and output services use `mcp.slurm.cpu` resources without requesting a GPU, including CPU-specific setup and extra arguments. Native prediction gets a separate GPU allocation using `mcp.slurm`. Finite CPU service reuse windows bound idle allocations. The worker bounds its pools and group admission; Slurm controls actual allocation. Keep one active driver per queue. The worker's job root, model assets and cache must be accessible from its CPU and GPU nodes. In the per-request compatibility path, CPU parents retain allocations while waiting for predictions.

For several SSH/local/Slurm/Kubernetes endpoints, use `mcp.backend: pool` and the [prediction server configuration](prediction-servers.md). With whole-request placement, each selected worker owns scientific preparation, cache reuse, prediction and scoring. The coordinator verifies final artifacts before cleanup and retains worker ownership through connection failures. Kubernetes uses finite CPU/GPU Jobs, explicit context/namespace, persistent storage and a bounded CPU gateway for remote file transfer.

## Monitoring and measurement

Validate the actual intended route on the execution host before a large campaign. A direct-scoring test does not exercise PubChem connectivity. Use production's CPU interpreter, environment, scientific runtime and scheduler profile. Test fresh inference when needed, verified collection, cache reuse and independent experimental scores. A cache-only canary does not establish GPU execution. Asset readiness in `server_info` describes configuration, not completed validation.

The first PubChem request is a production-route canary by default. Later requests remain queued until it succeeds. TLS, missing-dependency and model-configuration failures are classified; environment holds persist across reconnects without cancelling unrelated running work. `server_info` exposes admission scopes; held jobs include `admission_hold`. Repair the environment with TLS verification enabled, verify the CPU path, then call `resume_admission(scope, reason)`; the next queued request becomes the canary. Explicitly retry any failed attempts, preserving their evidence. Set a required, verified CA bundle through `mcp.worker_environment.SSL_CERT_FILE`. PubChem's request budget is shared across coordinator processes.

For large campaigns, CPU workers assemble compatible native manifests targeting 131,072 unique structure/actual-energy pairs per GPU job. Small requests and final remainders run below the 100,001-pair bulk goal; collection waits are bounded. Different energy sets can share a manifest while retaining exact per-structure energies. See [group sizing](prediction-servers.md#cpu-preparation-and-gpu-groups) for the controls and CPU output resource requirements.

For a batch, call `elucidate_spectra` once with the unknowns and verified settings, then poll their feature IDs. The backend prepares, groups, predicts and scores independently while accepting more requests. Individual search requests join the same backend queue. Start evidence review as each stable per-feature result arrives.

GPU children save `gpu-samples.csv` and `gpu-metrics.json`; `get_job` returns their `gpu_metrics`. `mcp.gpu_monitor_interval_seconds` sets the sampling interval (default 1 second, zero disables it). Samples use scheduler GPU IDs when available and include zeros, allocated-task timing, peak sampled memory and observed foreign compute processes. These whole-task measurements include startup, native preparation, writer drain and publication; derive sustained inference separately from native log boundaries and validate spectrum counts before calculating throughput.

`get_job` exposes `phase`, accumulated `phase_seconds` and the current `prediction_job`. Phases distinguish CPU preparation, waiting for a shared prediction, waiting for a GPU, GPU prediction, waiting for a CPU slot and CPU scoring. Poll the parent until terminal; an internal prediction completing does not mean experimental scoring has finished. See [job monitoring](job-monitoring.md).

For whole-request workers, `result_collection` means the worker has finished and the coordinator is transferring or validating its final artifacts. Transport statistics separate active operations, queued operations, retained entries and replies ready in each pool. Compare these with the worker's completion receipt when a parent appears stalled; recover verified results through collection before retrying inference.

For low GPU utilization or a long completion estimate, locate the slow phase before increasing GPU workers or batch size. Check CPU saturation, preparation queues, shared-cache waits, fragment merging and scoring as well as native inference timing. Stepped scoring decodes fragment masks once per temporary component and uses the native merge and normalization; raw cached spectra remain reusable when only this scoring calculation changes. Validate scoring optimizations against fixed saved predictions, comparing masses, intensities, fragment IDs, similarities, explained intensity and matched peaks exactly. Report a CPU replay speedup separately from measured inference or whole-workload gains. Keep fixes in the shared implementation and leave supplied model checkouts unchanged.

To measure an installation, freeze inputs, native source, weights and scientific settings, use separate cold prediction caches, and compare revisions on the same idle GPU. [The local benchmark script](../scripts/benchmark_mcp_pipeline.py) runs a fixed JSON request list through the selected local or pool backend and runner, records phase transitions and samples `nvidia-smi` utilization every 0.5 seconds. It excludes client transport and fixture preparation; endpoint transport is included when the pool backend is selected. Compare terminal feature accounting and hashes of peaks, fragments and scores as well as elapsed time. Sampled utilization is an observation, not a guarantee of saturation.

Report whole-workload utilization and sustained inference utilization separately. Use a representative prediction group large enough to measure many batches after startup, define the inference window from native logs, and include throughput, peak memory and sampling interval. A brief peak or an average over only nonzero samples does not establish sustained utilization. A short inference loop cannot diagnose CPU starvation or establish the best batch size; inspect native feature-wait, forward and writer-wait timing before changing the architecture.

The pipeline benchmark writes `inference_stages` for each GPU job: requested spectrum counts, runner telemetry, available native row counts/rates, and a native inference-window average that includes zero samples. `request_phase_seconds` reports CPU and wait phases separately. Native timing is unavailable when the predictor does not emit the recognized log format; do not substitute an active-only average. Fixed-input forward-prediction benchmarks omit formula search and experimental ranking. Also test the feature route with overlapping unknowns, a disconnected/reconnected client, verified cache publication and complete feature accounting before deploying a large analysis. Compare numeric spectra and peak-aligned fragment identities when exact hashes differ; native floating-point variation and peak ordering can change hashes.

Declare the mass/intensity tolerances before accepting a changed batching policy. Examine discrepant spectra individually; matching counts or a high average similarity does not establish equivalence for every structure. Keep the original cache and scientific settings when that check fails. Runner telemetry records its UTC offset for interpreting native logs collected from another host; older receipts without that field use the benchmark host's timezone.

[The scheduler benchmark](../scripts/benchmark_mcp_scheduler.py) exercises concurrent CPU handoffs on an isolated job root, including NFS, checking request accounting, waiting time and observed process bounds. It loads no models and does not measure GPU throughput. Keep explicit group-size overrides only when measured: a small override takes precedence over the duration target and causes frequent model restarts. Persistent model serving across features is not implemented.
