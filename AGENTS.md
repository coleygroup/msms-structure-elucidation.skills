# Agent instructions

This repository contains MS/MS structure elucidation skills and a Python CLI, `msms-structure-elucidation`. The skills are in `.agents/skills`, and `.claude/skills` links to the same folders.

- **Install or set up:** when asked to install these skills, or when `configs/local.yaml` is missing, follow the `msms-setup` skill. It checks the environment, asks whether models run on this machine or a remote host, probes that host, and saves the tuned ms-pred inference settings to `configs/local.yaml`. Do not commit that file.
- **Remote execution:** if `configs/local.yaml` has `execution.mode: remote`, run model-backed commands on that host as described in `msms-setup`. For multiple model hosts or Kubernetes, follow [prediction server pools](docs/prediction-servers.md). Keep endpoint identities, paths, contexts, namespaces and tuning in ignored local configuration. Collect final results to the user's computer before claiming local delivery.
- **Model tools:** when the `msms-structure-elucidation` MCP server is connected, call `server_info` first, then use its tools for predictions instead of running the model scripts directly.
- **Model and search selection:** use the intended prediction model and exact weights from a matching saved user confirmation, or ask once and save them; either ICEBERG's generator/intensity pair or a GLACIER checkpoint is sufficient. For ICEBERG, prefer suitable public atlas spectra unless fresh predictions throughout were requested. The atlas uses ICEBERG 2.1 trained on NIST'23; when local weights differ or matching weights are unverified, tell the user that combining their predictions may affect ranking comparability and label their sources. GLACIER predicts every candidate. For direct mass-only PubChem prediction, skip formula prediction, predict all eligible structures for every ppm-matched formula, and rank them together as described in `docs/technical-guide.md`.
- **Saved choices:** read [pipeline preferences](docs/pipeline-preferences.md) and `configs/local.yaml` before asking pipeline questions. Reuse matching user choices and verified acquisition settings, and save new ones with `msms-structure-elucidation preferences`. Without a supplied feature list or saved feature-finder answer, ask once: GNPS2 Everything Bagel (recommended), msconvert + MZmine, or the user's own workflow. Scientific answers apply only to their recorded dataset/spectrum context.
- **Formula search:** when no formula is supplied, recommend BUDDY’s top three formulas and ask once whether to use those or PubChem mass filtering. Reuse a matching explicit/saved choice; follow [formula search](docs/formula-search.md). Save the route, element filter and ppm tolerance with the dataset context.
- **Analysis:** follow [.agents/workflows/msms-elucidation.md](.agents/workflows/msms-elucidation.md). For raw/mzML inputs, inspect the relevant acquisition metadata first to establish energy values, NCE/eV units and separate versus stepped acquisition. Use verified saved settings for matching inputs; ask only when metadata is unavailable, ambiguous or conflicting. Follow [collision-energy handling](docs/collision-energy.md) and save provenance. Stepped acquisition predicts each component, merges intensities before normalization, and scores the composite once.
- **Running jobs:** keep monitoring queued/running jobs, including detached runs and resource waits, under [job monitoring](docs/job-monitoring.md). Review per-feature results as they become available and record their evidence while other jobs continue. Verify terminal states, full feature accounting and final artifacts before reporting completion.
- **Evidence review:** use [msms-evidence-review](.agents/skills/msms-evidence-review/SKILL.md) on stable results and after rescoring. Follow `pipeline.evidence_review` for bounded delegation when supported; reviewers assess complete features across all supplied energies and write separate drafts. The main agent keeps monitoring, checks and publishes accepted reviews, owns shared state and asks the user about optional routes. Review directly when delegation is unavailable.
- **Workflow completion hooks:** before launching an analysis, register it with the session ID supplied by the client hook and maintain its state under [workflow completion hooks](docs/workflow-hooks.md). Register every job and requested feature, link current evidence reviews and scoped user decisions, and run `msms-workflow-guard finish` before reporting completion. Continue authorized work when the Stop hook identifies missing requirements. Register no run for ordinary questions, setup-only tasks or repository edits. Explicit pauses and genuine scoped holds must be recorded; do not delete state or invent evidence to pass the checker.
- **Standards:** code, skills, workflows and research conduct follow `.agents/rules/`. For batch sizes and worker counts, use settings measured for the selected model in `configs/local.yaml`. For ICEBERG, start with two parallel GPU workers per GPU and tune two to four within memory limits. For GLACIER, keep one prediction process per GPU and primarily tune batch size through its native `pred_smis` path. Measure sustained inference utilization separately from whole-workload utilization. GLACIER starts with batch size 128, 4 CPU workers, 1 GPU worker and 1 prediction process per GPU, 2 HDF5 writers, 4 HDF5 chunks, feature cache 256 and sparse peaks 100 under `models.simulator.glacier`. Reuse compatible raw predictions across unknowns through the shared model-host cache; always score each unknown separately.
