# MS/MS structure elucidation

Read [saved pipeline preferences](../../docs/pipeline-preferences.md) before asking questions. Reuse user-confirmed answers within their recorded scope and context; save new answers in the local config. Defaults and inferred metadata are not confirmations.

Before choosing a retrieval or prediction path, confirm the intended model and exact weights using `msms-setup`; either ICEBERG's generator/intensity pair or a GLACIER checkpoint is sufficient. Choose supplied formulas, MSBuddy hypotheses, or a [mass-only PubChem search](../../docs/technical-guide.md#mass-only-pubchem-option). The mass-only route skips MSBuddy and other formula prediction, collects all eligible structures for every formula matched within the adduct-corrected mass tolerance, predicts every candidate with the confirmed model, and ranks them together. Check retrieval limits, preserve formula/mass-error provenance, and report incomplete coverage.

Use public atlas spectra only for the ICEBERG route and only when fresh predictions throughout were not requested. GLACIER has no open atlas available: predict/score every candidate with the confirmed GLACIER weights. Prefer suitable atlas spectra for ICEBERG. They were generated with ICEBERG 2.1 trained on NIST'23; if local weights differ or matching weights are unverified, tell the user that mixing their predictions may affect ranking comparability and identify each source. Keep direct predictions on the confirmed weights, and tune GLACIER independently on each host. The CLI `run` and `batch` routes use atlas retrieval by default. For mass-only searches, use `--mass-only --ms1-ppm <tolerance> --model <confirmed-model>` on either command; it predicts all eligible PubChem mass matches and ranks them across formulas, writing the standard reports and resumable shards. With MCP connected, call `server_info` first, then `search_pubchem_mass` with the confirmed model, ppm and collision unit. For an explicit candidate list, use `score_candidates` with the confirmed model and a formula per group. CLI `review` can retain or reuse ICEBERG scores even with `--model glacier`; it does not provide a full GLACIER rescore.

1. For LC-MS input without a supplied feature list, feature table/MGF or selected MS/MS spectra, read the saved feature-finder choice and follow `msms-feature-detect`. On the first such run, ask once: GNPS2 Everything Bagel (recommended default), msconvert + MZmine, or the user's own workflow; save and reuse the answer. `msms-inspect` is optional and preprocessing is needed only when the selected workflow requires conversion or polarity splitting. For GNPS2 Everything Bagel exports, keep the aligned feature table with its MGF, verify `SCANS` against table `row ID`, and add `--feature-id-field SCANS` to conversion. Process polarities separately and obtain energy-separated spectra if the export merged different energies. For GNPS/MZmine MGF, use `msms-structure-elucidation convert-mgf --input features.mgf --collision-unit eV --output-dir converted`; supply `--raw-mzxml` with the raw mzXML files or their folder to recover collision energies from referenced MS2 scans or, for GNPS exports that name only `SOURCE_FILE`, from that run's MS2 scans of the same precursor within `--ms2-rt-window` seconds (default 30). Convert the whole MGF and select features with `--feature-ids`. The converter uses every co-eluting feature to assign adducts ([M+Na]+, [M+NH4]+ and others) and to set aside multimers and in-source fragments, with the evidence in the manifest. Report those statuses and their related features rather than elucidating them as molecules. When atlas spectra do not cover the experimental adduct, predict candidates for that adduct with the selected model. `SOURCE_SCAN`/`SCANS` may be the MS1 apex and must not be treated as an MS2 scan. A `needs_energy` manifest row requires provider confirmation or an explicit `--energy` override. For Bruker Q-TOF, inspect the raw MS2 scan's precursor-specific absolute eV setting. For an existing `.ms` file, proceed directly.
2. Reuse the recorded collision energies and NCE/eV unit for the matching dataset/spectrum context. Ask only for missing or conflicting information and save the answer with that context. Do not infer the unit from the `.ms` headers, instrument, or numeric values; report any conflict between the user answer and headers. For the ICEBERG atlas route, run `msms-structure-elucidation run --input sample.ms --collision-unit NCE --output-dir results/sample` (or `--collision-unit eV` when confirmed). Supply `--formula` when known, or `--formulas-file` for a list. On this atlas route, otherwise the top three MSBuddy hypotheses are searched and recorded as inferred. For a mass-only search, add `--mass-only --ms1-ppm <tolerance> --model <confirmed-model>` and omit explicit formula options; MSBuddy and atlas retrieval are skipped even if the `.ms` header has a formula. MSBuddy mass tolerances follow the instrument: Q-TOF 10 ppm precursor / 20 ppm fragments, Orbitrap 5 / 10 ppm; an unrecognised instrument gets the Q-TOF values and a warning. Override with `--ms1-ppm`/`--ms2-ppm`; the values used are recorded as `mass_tolerance`. If MSBuddy proposes none, `run` searches PubChem for single-component, uncharged, closed-shell structures within the precursor tolerance (CHNOPS by default; `--formula-elements`) and searches up to three of their formulas, recorded as PubChem mass matches. If there is still no formula, report `needs_formula` (`next_step: review-frigid`): review the spectrum yourself (adduct, in-source fragment, isotope peak, noise), request formula evidence or a formula list, and decide whether FRIGID (step 5) is warranted.
3. Read `retrieval.json`, especially `status`, `formula_results`, and `energy_mapping`. Public atlas entries are precomputed ICEBERG 2.1 predictions for PubChem structures and omit licensed NIST structures. Convert confirmed NCE to eV, round both experimental and atlas eV to integers, and use only exact rounded matches. If any energy is absent for an atlas formula, local ICEBERG predicts all atlas structures for that formula at every supplied energy in resumable shards. Supply an ms-pred checkout and public or licensed ICEBERG weights; if missing, report `blocked_model_assets` and the underlying error. Inspect that every experimental energy contributed to the score. Similarity near or below 0.5 is a review trigger, not calibrated confidence. Explain `no_atlas_coverage` separately from weak matches; its `next_step: iceberg-pubchem` means predicting the formula's PubChem structures with `msms-structure-elucidation review --result results/sample/retrieval.json --proposals pubchem --model iceberg`.
4. When evidence is weak or important peaks remain unexplained, use `msms-structure-review` for agent-led structural hypotheses: build a candidate-specific matched/unmatched peak table, propose explicit connectivity edits, and save `proposals.json` with a companion `proposal_evidence.json` recording the observations and reasoning. These are new candidates relative to the current pool, not a claim of database or literature novelty. The CLI `review` validates and scores supplied SMILES; it does not generate them. Validate formulas and duplicates, then score with the user-confirmed model and weights and compare newly explained peaks, lost matches and remaining discrepancies. Use `msms-denovo` when trained spectrum-to-structure generation is required. For ICEBERG, suitable atlas matches may be reused unless fresh predictions throughout were requested. For GLACIER, rescore all candidates directly instead of using CLI `review` to extend an ICEBERG ranking. Set `--ms-pred-dir` to the checkout so relative model scripts run correctly; the checkpoint preflight catches incompatible GLACIER atom feature widths. Use `.ms >instrumentation` or `--instrument`, and `--cuda-devices` or `MSMS_CUDA_DEVICES` for GPU. Convert NCE to rounded integer eV with `nce=False`. Model failure is fatal and prints the underlying error. If several experimental energies round to the same model eV, predict that eV once and compare it with each experimental spectrum. Simulated candidates record the model name and version (e.g. ICEBERG 2.1), ms-pred version, and checkpoint.
5. If no satisfactory candidate emerges, run `msms-subformulae` then `msms-denovo` with FRIGID. Keep FRIGID's interpreter and checkpoint paths separate from ms-pred; the setup script clones and installs FRIGID without modifying an existing checkout.
6. Always present the richer `msms-visualize` page as the primary result, including when `run` also wrote a basic `report.html`. Run `msms-structure-elucidation visualize --result results/sample/retrieval.json` and give the user its localhost URL. For several unknowns, pass every `retrieval.json` to one viewer so all of them are reviewed on a single page. The viewer shows ranked candidates, all paired collision energies, mirror spectra, and clickable predicted fragments; candidate decisions and fragment comments autosave to a separate `review_notes.json`. For a shareable snapshot with the same rich interaction, use `visualize --result ... --export review_report.html`.
7. For many features, use `batch --mass-only --ms1-ppm <tolerance> --model <confirmed-model>` for direct mass search, or for the ICEBERG atlas route run `msms-structure-elucidation batch --manifest converted/manifest.csv --output-dir results/batch` It processes several features at once in worker processes when CPU and RAM permit (`max_workers: auto`, up to 8, or the value `setup` saved), so atlas lookups run in parallel and the GPU is not left idle during one feature's CPU steps. Lower `--max-workers` if memory is tight. When every feature is done, batch exports one self-contained `review_report.html` for all results in the output directory and prints the `visualize` command; present that page (or the served viewer, `--serve`) as the batch result. `--no-review-page` skips it. Report candidate source, formula source, entropy score, explained intensity, positional-isomer ambiguity, matched and unexplained peaks, model asset provenance, per-formula status, and limitations. Preserve candidate evidence in JSON and HTML.
