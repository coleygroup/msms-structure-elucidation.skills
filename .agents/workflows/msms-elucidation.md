# MS/MS structure elucidation

Read [saved pipeline preferences](../../docs/pipeline-preferences.md) before asking questions. Reuse verified acquisition settings and user-confirmed choices within their recorded scope and context; save their provenance in the local config. Defaults and guesses are not confirmations.

Before choosing a retrieval or prediction path, confirm the intended model and exact weights using `msms-setup`; either ICEBERG's generator/intensity pair or a GLACIER checkpoint is sufficient. Use supplied formulas when available. Otherwise follow [formula search](../../docs/formula-search.md): recommend BUDDY’s top three formulas and ask once whether to use them or PubChem mass filtering, unless an explicit request or matching saved answer already selected the route. Save `formula_strategy`, the element filter and ppm tolerance with the input context. Do not treat the default recommendation as user confirmation. The mass-only route skips MSBuddy and other formula prediction, collects all eligible structures for every formula matched within the adduct-corrected mass tolerance, predicts every candidate with the confirmed model, and ranks them together. Check retrieval limits, preserve formula/mass-error provenance, and report incomplete coverage.

Use public atlas spectra only for the ICEBERG route and only when fresh predictions throughout were not requested. GLACIER has no open atlas available: predict/score every candidate with the confirmed GLACIER weights. Prefer suitable atlas spectra for ICEBERG. They were generated with ICEBERG 2.1 trained on NIST'23; if local weights differ or matching weights are unverified, tell the user that mixing their predictions may affect ranking comparability and identify each source. Keep direct predictions on the confirmed weights, and tune GLACIER independently on each host. The CLI `run` and `batch` routes use atlas retrieval for ICEBERG formula searches; GLACIER retrieves and predicts PubChem candidates for each selected formula. Reuse matching raw candidate spectra across unknowns through the shared prediction cache, checking structure, weights, adduct, instrument, actual model eV and scientific settings. Never reuse experimental scores or matched peaks between unknowns. For mass-only searches, use `--mass-only --ms1-ppm <tolerance> --model <confirmed-model>` on either command; it predicts all eligible PubChem mass matches and ranks them across formulas, writing the standard reports and resumable shards. With MCP connected, call `server_info` first, then `search_pubchem_mass` with the confirmed model, ppm and collision unit. For an explicit candidate list, use `score_candidates` with the confirmed model and a formula per group. CLI `review` can retain or reuse ICEBERG scores even with `--model glacier`; it does not provide a full GLACIER rescore.

After the user selects BUDDY and an MCP server is connected, use `infer_formulas` for its top three hypotheses. For GLACIER, use `search_pubchem_formulas` on the selected formulas; for ICEBERG, use `retrieve_atlas`. Use `search_pubchem_mass` for the selected mass-filtering route.

**Register and maintain the analysis.** Before feature finding or model work, register the requested inputs/features using [workflow completion hooks](../../docs/workflow-hooks.md) and the session ID supplied by the client hook. Register every launched job, maintain evidence-backed prerequisites and per-feature outcomes, and finalize through `msms-workflow-guard finish`. When a Stop hook reports unfinished work, inspect the actual artifacts and continue the applicable steps. Record explicit user pauses or genuine scoped holds without treating them as completion.

**Monitor execution and review incrementally.** Keep monitoring queued/running jobs after launch, including detached jobs and resource waits. As each feature result becomes available, review it while the rest continue; do not wait for the whole dataset or the final report. Follow [job monitoring and early review](../../docs/job-monitoring.md), keep the user informed, and verify the requested output and coverage before reporting completion.

1. For LC-MS input without a supplied feature list, feature table/MGF or selected MS/MS spectra, read the saved feature-finder choice and follow `msms-feature-detect`. On the first such run, ask once: GNPS2 Everything Bagel (recommended default), msconvert + MZmine, or the user's own workflow; save and reuse the answer. `msms-inspect` is optional and preprocessing is needed only when the selected workflow requires conversion or polarity splitting. For GNPS2 Everything Bagel exports, keep the aligned feature table with its MGF, verify `SCANS` against table `row ID`, and add `--feature-id-field SCANS` to conversion. Process polarities separately. For a known stepped acquisition, preserve its component list using the collision-energy procedure; otherwise resolve merged-energy metadata before scoring. For GNPS/MZmine MGF, use `msms-structure-elucidation convert-mgf --input features.mgf --collision-unit eV --output-dir converted`; supply `--raw-mzxml` with the raw mzXML files or their folder to recover collision energies from referenced MS2 scans or, for GNPS exports that name only `SOURCE_FILE`, from that run's MS2 scans of the same precursor within `--ms2-rt-window` seconds (default 30). Convert the whole MGF and select features with `--feature-ids`. The converter uses every co-eluting feature to assign adducts ([M+Na]+, [M+NH4]+ and others) and to set aside multimers and in-source fragments, with the evidence in the manifest. Report those statuses and their related features rather than elucidating them as molecules. When atlas spectra do not cover the experimental adduct, predict candidates for that adduct with the selected model. `SOURCE_SCAN`/`SCANS` may be the MS1 apex and must not be treated as an MS2 scan. A `needs_energy` manifest row requires provider confirmation or an explicit `--energy` override. For Bruker Q-TOF, inspect the raw MS2 scan's precursor-specific absolute eV setting. For an existing `.ms` file, proceed directly.
2. First inspect supplied raw/mzML acquisition metadata yourself for the relevant precursor/MS2 scans, including energy values, units and whether the acquisition is stepped. Use `inspect-energy` and the [collision-energy procedure](../../docs/collision-energy.md), or reuse settings verified for the same input context. Ask the user only if the settings cannot be resolved or evidence conflicts; never guess from instrument names, numbers or `.ms` labels alone. Save the values and their metadata/user provenance. For one stepped spectrum, predict all explicit components, merge their intensities before final normalization, and score the merged prediction once; retain separate per-energy comparisons for separately acquired spectra. For the ICEBERG atlas route, run `msms-structure-elucidation run --input sample.ms --collision-unit NCE --output-dir results/sample` (or `--collision-unit eV` when confirmed). Supply `--formula` when known, or `--formulas-file` for a list. On the selected BUDDY route, otherwise up to three ranked formulas are searched and recorded as inferred. For GLACIER use `run --model glacier` without `--mass-only` to predict the PubChem candidates of those selected formulas, or with `--formula` / `--formulas-file` for supplied hypotheses. For a mass-only search, add `--mass-only --ms1-ppm <tolerance> --model <confirmed-model>` and omit explicit formula options; MSBuddy and atlas retrieval are skipped even if the `.ms` header has a formula. MSBuddy mass tolerances follow the instrument: Q-TOF 10 ppm precursor / 20 ppm fragments, Orbitrap 5 / 10 ppm; an unrecognised instrument gets the Q-TOF values and a warning. Override with `--ms1-ppm`/`--ms2-ppm`; the values used are recorded as `mass_tolerance`. If BUDDY/MSBuddy proposes no formula, explain that result and ask whether to switch to mass filtering. The default CLI does not switch automatically; `--pubchem-fallback` is an explicit opt-in to the limited formula fallback. For the user-selected full mass-filtering route, use `--mass-only`, retaining every eligible formula. Its default elements are C, H, N, O, P, S, F, Cl, Br, I, Si, B and Se; `--formula-elements` overrides them. If there is still no formula, report `needs_formula` and the recorded `next_step` (choose a formula/mass route, or review FRIGID after exhausted searches): review the spectrum yourself (adduct, in-source fragment, isotope peak, noise), request formula evidence or a formula list, and decide whether FRIGID (step 5) is appropriate. Require the post-step-3 user choice and a target formula before running it.
3. Read `retrieval.json`, especially `status`, `formula_results`, and `energy_mapping`. Public atlas entries are precomputed ICEBERG 2.1 predictions for PubChem structures and omit licensed NIST structures. Convert confirmed NCE to eV, round both experimental and atlas eV to integers, and use only exact rounded matches. If any energy is absent for an atlas formula, local ICEBERG predicts all atlas structures for that formula at every supplied energy in resumable shards. Supply an ms-pred checkout and public or licensed ICEBERG weights; if missing, report `blocked_model_assets` and the underlying error. Inspect that every experimental energy contributed to the score. Similarity near or below 0.5 is a review trigger, not calibrated confidence. Explain `no_atlas_coverage` separately from weak matches; its `next_step: iceberg-pubchem` means predicting the formula's PubChem structures with `msms-structure-elucidation review --result results/sample/retrieval.json --proposals pubchem --model iceberg`.

   **Agent review.** Apply step 3 and this review to each feature as its result becomes available; the whole batch does not need to finish first. Use [msms-evidence-review](../skills/msms-evidence-review/SKILL.md) to review every result, including high-scoring candidates. Delegate ready batch reviews to a bounded pool when available, following the skill and `pipeline.evidence_review`; otherwise review directly. The main agent keeps monitoring jobs, checks reviewer drafts and publishes the accepted per-feature reviews. Compare the leading candidates' matched and unexplained peaks across all supplied energies, assess the supporting evidence and remaining ambiguities, and record the assessment in a per-feature `evidence_review.json`. Label reviews of incomplete candidate/energy coverage as provisional and refresh them when the result changes. Continue monitoring other jobs between reviews. Follow the [evidence-review checklist](../skills/msms-evidence-review/references/evidence-review.md).

   Keep the skill's [continuous review queue](../skills/msms-evidence-review/references/review-queue.md) moving: refill available reviewer slots from newly ready features and required refreshes, publish each accepted assessment promptly, and keep deeper investigations in a separate follow-up queue. Preserve the full review checklist and keep monitoring predictions while reviews run.

   **User choice for weak entries.** If evidence is weak or important peaks remain unexplained, summarize the affected entries and ask which optional route the user wants:

   | Choice | Route |
   |---|---|
   | **4** | Agent proposals, validated and scored with ICEBERG/GLACIER |
   | **5** | FRIGID de novo, followed by ICEBERG/GLACIER scoring |
   | **Both** | Run both routes and compare their combined candidates |
   | **Skip** | Report the current hypotheses and unresolved evidence |

   Ask for ready entries or an identified subset without waiting for the rest of the batch. Wait for the user's choice before either optional route, unless an explicit prior choice already covers the same analysis and entries; keep monitoring and reviewing unaffected jobs while waiting. Group entries into one question when practical, allowing different choices for subsets. Save `denovo_route` (`agent`, `frigid`, `both` or `skip`) with its analysis/entry context using [pipeline preferences](../../docs/pipeline-preferences.md), and record the choice separately from the agent's assessment. If no follow-up is needed or the user skips, proceed to step 6.

4. **Agent proposals (if selected).** For entries assigned `agent` or `both`, use `msms-structure-proposal` to propose SMILES from the reviewed peak evidence and save `proposals.json` with `proposal_evidence.json`. Validate formulas and duplicates, use `msms-predict` to score with the confirmed ICEBERG or GLACIER model, then use `msms-evidence-review` to assess whether the proposals explain the disputed peaks. The detailed procedures are in those skills.
5. **FRIGID de novo (if selected).** For entries assigned `frigid` or `both`, verify the target formula and run `msms-subformulae` then `msms-denovo`. Validate and deduplicate the generated SMILES, score them with the confirmed ICEBERG or GLACIER model, and use `msms-evidence-review` again. Keep FRIGID's environment and checkpoints separate from ms-pred as described in the skill.

   If `both` was selected, complete both routes and compare their combined candidates under the same scoring policy, retaining each proposal's origin. Do not automatically switch to an unselected route when one fails to improve the result.

6. Always present the richer `msms-visualize` page as the primary result, including when `run` also wrote a basic `report.html`. Run `msms-structure-elucidation visualize --result results/sample/retrieval.json` and give the user its localhost URL. For several unknowns, pass every `retrieval.json` to one viewer so all of them are reviewed on a single page. The viewer shows ranked candidates, all paired collision energies, mirror spectra, and clickable predicted fragments; candidate decisions and fragment comments autosave to a separate `review_notes.json`. For a shareable snapshot with the same rich interaction, use `visualize --result ... --export review_report.html`.
7. For many features, use `batch --mass-only --ms1-ppm <tolerance> --model <confirmed-model>` for direct mass search, or for the ICEBERG atlas route run `msms-structure-elucidation batch --manifest converted/manifest.csv --output-dir results/batch` It processes several features at once in worker processes when CPU and RAM permit (`max_workers: auto`, up to 8, or the value `setup` saved), so atlas lookups run in parallel and the GPU is not left idle during one feature's CPU steps. Lower `--max-workers` if memory is tight. During execution, review stable per-feature outputs and show a clearly labelled partial viewer when useful. The batch exporter writes one self-contained `review_report.html` after the batch ends; that export timing does not postpone agent review. Verify the final page and feature accounting before presenting it (or the served viewer, `--serve`) as the completed batch result. `--no-review-page` skips it. Report candidate source, formula source, entropy score, explained intensity, positional-isomer ambiguity, matched and unexplained peaks, model asset provenance, per-formula status, and limitations. Preserve candidate evidence in JSON and HTML, and include the conclusions, selected optional route (including skip), and remaining uncertainties from `evidence_review.json` in the final assessment.
