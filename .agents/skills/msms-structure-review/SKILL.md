# Structure review and candidate proposals

Use when strong peaks remain unexplained, candidate structures are difficult to distinguish, or the user asks for new structural hypotheses. The agent applying this skill performs the structural reasoning and writes proposals. The CLI `review` command validates and scores supplied SMILES; it does not generate them from peaks. `--proposals pubchem` expands a database candidate pool. For a trained spectrum-to-structure generator, use `msms-denovo` with FRIGID.

In the elucidation workflow, automatic evidence assessment follows retrieval/scoring. Begin this skill's proposal-and-scoring phase only when the user selected the agent route or both routes for the affected entries, or directly requested these proposals. Respect a FRIGID-only or skip choice; ask about changing routes rather than switching automatically. Reuse a saved selection only within its recorded analysis/entry context.

A new proposal is a connectivity absent from the current candidate pool. Establishing that a molecule is absent from databases or the literature requires a separate search; do not claim chemical novelty from this workflow alone.

## Confirm the comparison settings

Keep the prediction model and exact weights confirmed in `msms-setup`. With MCP connected, call `server_info` first and use `score_candidates` with an explicit `model` and the target `formula`. For GLACIER or a request for fresh predictions throughout, score the complete candidate pool directly with the selected model and weights. For a [mass-only PubChem search](../../../docs/technical-guide.md#mass-only-pubchem-option), use `run --mass-only --ms1-ppm <tolerance> --model <confirmed-model>` or the MCP `search_pubchem_mass` tool; it skips formula prediction and atlas reuse, scores all eligible structures for every matched formula, and combines their scores.

For ICEBERG, prefer suitable atlas spectra. The atlas uses ICEBERG 2.1 trained on NIST'23; if local weights differ or matching weights are unverified, tell the user that combining their predictions may affect ranking comparability and label the sources. The CLI `review` command extends an existing result: it retains candidates, reuses suitable atlas matches and predicts additional structures. Use direct `score_candidates` calls for a ranking based entirely on one selected model and checkpoint.

## Derive proposals from peak evidence

Use the [evidence-review checklist](references/evidence-review.md) to assess the current ranking before proposing structures. Reuse its candidate-specific evidence and update it after scoring.

1. **Establish the input constraints.** Read the original experimental `.ms` file, `retrieval.json` and any `review_notes.json`. Reuse matching saved confirmations for collision units, adduct, instrument, model and exact weights as described in [pipeline preferences](../../../docs/pipeline-preferences.md). Record the target neutral formula and whether it was supplied or inferred. Keep different formula hypotheses in separate proposal groups. If formula, precursor, adduct or collision metadata conflict, resolve that before structural edits.
2. **Build a candidate-specific evidence table.** For each leading candidate, list the measured m/z, experimental collision energy, intensity and matched/unmatched status of the peaks that will guide the review. Read its `matched_peaks`, `energy_alignment`, predicted spectra and available fragment assignments. Use `msms-visualize` to inspect atom-level assignments. `review_evidence` is a starting summary for its named `best_candidate`; its unexplained list contains only the strongest 20 peaks and may describe an earlier ranking after review. Verify it against the current candidate and full experimental spectrum, and reconstruct the table when needed. Report missing energy comparisons instead of treating them as structural evidence.
3. **Turn the observations into constraints.** Identify which substructures or connectivity patterns are supported by several matched fragments, and which strong unexplained peaks require a different explanation. Check fragment subformulae and compatible neutral losses when useful; `msms-subformulae` can supply formula-constrained assignments. Calculate mass errors using the stated tolerance and correct ion/charge conventions. Keep ambiguous assignments as alternatives. A predicted fragment or coincident m/z is a hypothesis, not proof of a fragmentation mechanism. Check precursor leakage, isotopes, co-isolation and noise before using an unmatched peak to demand a new substructure.
4. **Write explicit graph hypotheses.** Start from supported parts of leading structures and propose a small, diverse set of plausible connectivity changes that could explain the selected unmatched peaks while preserving useful matches. Consider alternative attachment positions, linkages, ring arrangements or functional-group placements only when the evidence motivates them. Recheck the complete formula after every edit. If no leading scaffold is supported, construct alternative formula-constrained scaffolds from the fragment constraints and mark the greater uncertainty. For each proposal, name the reference candidate, the exact graph change, the measured peaks it aims to explain or retain, and a matched peak or competing observation that could argue against it. Avoid unsupported stereochemical assignments. Do not invent peak masses, fragment formulas or mechanisms to justify a preferred structure.
5. **Create and validate the proposal files.** Write `proposals.json` as a JSON array of SMILES strings, which is the input accepted by `review --smiles-json`. Write a companion `proposal_evidence.json` containing each proposal's formula, reference SMILES, graph edit, observed peak evidence (energy, m/z, intensity and match status), proposed assignments, expected gains, counterevidence and origin (`agent`, `user`, `pubchem` or `frigid`). Keep calculated quantities distinct from observations. Validate with RDKit in the configured model environment: parse/sanitize each structure, calculate its formula and charge, check that it is an appropriate single candidate molecule, and canonicalize/deduplicate by connectivity against both the proposal set and existing candidates. Keep rejected proposals and their reasons in the evidence file. The CLI repeats SMILES/formula validation before scoring; it reads only `proposals.json`, so maintain the companion evidence file explicitly.
6. **Score and test the hypotheses.** Use the scoring route below and compare each proposal against the reference candidates with the same experimental peaks, adduct, instrument, supplied energies and confirmed model policy. Report entropy similarity, explained intensity, newly matched peaks, lost matches and remaining strong unexplained peaks by energy. A higher aggregate score alone does not establish the proposed graph change or resolve positional isomers. Update `proposal_evidence.json` with the measured scoring outcome and show the combined review in `msms-visualize`. Rebuild candidate-specific evidence before another proposal round. Continue only when a concrete unresolved observation motivates another test; otherwise report the remaining ambiguity. Use `msms-denovo` only if the user also selected FRIGID or directly requests that route.

If no defensible structural proposal follows from the available peaks, say so and retain the current candidates and evidence. The 0.5 weak-match flag is a review heuristic, not identification confidence.

## Score supplied proposals


For `next_step: iceberg-pubchem` (no ICEBERG Atlas entry for the formula), pass `--proposals pubchem` instead of `--smiles-json` to predict PubChem's single-component, uncharged structures of the formula (`--max-structures`, default 500; `--formula` picks one of several searched formulas). For `next_step: review-frigid`, no formula was found by MSBuddy or by a PubChem mass search: review the spectrum and decide whether FRIGID de novo generation (`msms-denovo`) is warranted. Proposals are matched to atlas entries by InChIKey connectivity, because the atlas stores SMILES without stereochemistry. Each simulated candidate records `model_name`, `model_version` (from ms-pred's `model_registry`, e.g. ICEBERG 2.1), `ms_pred_version`, and `model_checkpoint`; report them with the result.

For local GLACIER or ICEBERG inference, clone [coleygroup/ms-pred](https://github.com/coleygroup/ms-pred) if needed, read the checkout's `README.md` **Install & setup** section, and follow its instructions for the host's CPU or CUDA environment. Reuse a verified existing interpreter when available and pass it with `--ms-pred-python`. Set `--ms-pred-dir` to the checkout; GLACIER launches a relative script from there. Save recurring checkout and checkpoint paths in the uncommitted `configs/local.yaml`.

```bash
msms-structure-elucidation review \
  --result results/sample/retrieval.json \
  --smiles-json results/sample/proposals.json \
  --ms-pred-dir /path/to/ms-pred \
  --model iceberg \
  --gen-checkpoint /path/to/gen.ckpt --inten-checkpoint /path/to/inten.ckpt
```

The command canonicalizes SMILES, rejects formula mismatches and duplicates, reuses exact-energy atlas matches, then simulates absent structures. Set `--model` explicitly to the selected model. ICEBERG needs generator and intensity checkpoints; GLACIER needs one checkpoint. When the result has multiple formulas, use `--formula` to select the formula for proposals. Model inputs are rounded integer eV after confirmed NCE conversion and use `nce=False`. `.ms >instrumentation` supplies the instrument unless `--instrument` overrides it; `--cuda-devices` or `MSMS_CUDA_DEVICES` enables GPU selection. Use settings measured for the selected model on this host. The anchors in `msms-predict` (**Inference configuration anchors**) apply to ICEBERG; tune GLACIER's native `pred_smis` batch size and CPU workers independently as described in `msms-setup`. The current GLACIER adapter uses one GPU worker. GLACIER checkpoint atom feature width is checked before inference. Model subprocess failure is fatal, prints its output, and leaves the prior result untouched. Generated candidates record `model_collision_energies_ev`. Public MassSpecGym weights are linked in the [ms-pred README](https://github.com/coleygroup/ms-pred#readme); use locally supplied NIST weights only if licensed. The offline HTML report is refreshed after a successful review. Use `msms-visualize` to inspect fragment assignments and save review notes.
